# 多项目知识管理的经验

以下只保留可复用取舍，不携带原项目源码、当前发布 ID、业务数据或凭据。

| 项目 | 遇到的情况 | 可复用做法 |
| --- | --- | --- |
| Skill 管理项目 | 历史入口与当前入口混杂，早期 MCP 返回量过小 | 明确状态来源与旧入口边界，find→read；放宽返回预算并保证续读完整 |
| 业务看板项目 | 大父目录混有其他内容，月结、费用和建设历程来源分散，源码/生产/采集 Skill 版本不一致 | 先建立聚焦工作区和来源导航；只收当前范围的维护资料，分清发布包、本地维护和运行环境版本 |
| Agent 评测项目 | 大量录制、产物和副本，旧文档与最新回放/消费端代码不同 | 只收小批维护资料，补当前契约和完成证据，隔离被测 Agent 与答案；源码归一另行维护 |

## 应当默认保留

- 小白名单与原路径/选区/指纹：后续排查“为什么回答错”时能直接定位原文。
- 原文 SHA256 回读：导入成功不能保证 canonical 文件是预期原文。
- 状态优先级与完成边界：同文件中的失败、等待和最终完成不可一起当当前事实。
- 当前来源冲突阻断：结构化 JSON 已更新而 CURRENT 未更新时不导入矛盾状态；契约代码变化须重新核对，不能继续用旧文档假装最新。
- 无变化不生成摘要/向量；去掉运维段可避免仅调工具预算触发知识重建，但保留后续有日期业务规则。
- 同步 journal、锁与已提交任务恢复：网络结果未知先查任务，不盲重提；多项目共用服务串行写，读请求独立路由。
- 注册与定时列表分离：新增未验收项目不会自动进入每日任务。

## 两个架构选择不要混淆

多个项目共用一个全局 `openviking` MCP，通过显式 project_code/workspace_path 路由；项目可以各用独立账号。新电脑沿用这一全局 MCP 入口，后续新增项目不用再注册 MCP。三个模拟项目已验证原生跨账号隔离，这一验证不等于共享账号也有原生隔离。可迁移包默认保留“一个全局 MCP + 项目独立账号”，用户明确选择 shared 时才共享身份。共享身份的 URI/工作区检查是工具约束，不是服务原生账号隔离，更不是 macOS/Linux 文件系统隔离。

## 安装与模型

不要把公司某个 provider 名、机器路径或模型当成通用默认。摘要模型和 embedding 的可用权限独立，曾出现聊天已通过但 embedding 未绑定的 403；首次 probe 既检查权限，也记录向量维度。模型的推理开销和输出预算应与摘要任务相称。

GitHub 不通先走 wheel/PyPI 镜像；不要为了安装知识服务默认铺 Rust/C++ 工具链，也不要把未知公共代理当作凭据通道。离线除了 wheel，还要验证 tokenizer 表、时区与原生组件。

## 尚不能推广成结论的内容

小规模检索题通过只证明这些资料可被找到并读回，不证明全项目回答准确率，也不证明整任务省多少 token。首次建库和布局修复会产生一次性模型成本；跨电脑、其他 OS、GUI 原生工具调用和未来定时运行应分别验证，不以本机协议联调代替。
